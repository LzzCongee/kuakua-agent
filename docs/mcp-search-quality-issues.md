# MCP 语义搜索质量问题分析

## 问题概述

Supermemory MCP 服务的 `search_memory` 接口在中文短文本场景下存在语义召回质量不稳定的问题，导致注入 prompt 的记忆与当前用户输入无关，进而影响 LLM 回复质量。

## 核心问题：Embedding 模型中文短文本区分度不足

### 典型案例 1："有问题" → "测试"（语义混淆）

| 字段 | 值 |
|------|-----|
| Query | `还是有问题这个功能` |
| 用户意图 | 反馈当前功能存在 bug/缺陷 |

MCP 返回的 top 5 结果：

| Score | Memory | 相关性 |
|-------|--------|--------|
| 0.664 | 修复后进行测试 | 无关 |
| 0.659 | 修复后测试成功 | 无关 |
| 0.644 | 用户表示正在进行测试用途 | 无关 |
| 0.643 | 用户说：areu ok | 无关 |
| 0.637 | AI对用户的问题进行了回复 | 无关 |

**分析**：用户说"有问题"，embedding 模型将其映射到"修复/测试"语义簇。这5条记忆对生成回复毫无帮助，注入 prompt 后反而会误导 LLM（让 LLM 以为用户在讨论测试相关话题）。

### 典型案例 2：英文近音词召回质量差

| 字段 | 值 |
|------|-----|
| Query | `holy shi` |

MCP 返回的 top 5 结果：

| Score | Memory | 相关性 |
|-------|--------|--------|
| 0.660 | 用户说：hi | 弱相关 |
| 0.622 | 用户说：hello | 弱相关 |
| 0.604 | 用户使用了"holaaa"作为打招呼的方式 | 弱相关 |
| 0.593 | 用户说：areu ok | 无关 |
| 0.553 | 用户使用"holaaa"打招呼，显示出俏皮的一面 | 弱相关 |

**分析**：`holy shi` 是口语化表达（可能是"holy shit"的变体或语气词），但搜索被错误导向了"hi"/"hello"等简单问候。最高分仅 0.66。

### 典型案例 3：相关查询工作正常

| 字段 | 值 |
|------|-----|
| Query | `继续测试一下` |

| Score | Memory | 相关性 |
|-------|--------|--------|
| 0.824 | 修复后进行测试 | 相关 |
| 0.758 | 用户表示正在进行测试用途 | 相关 |
| 0.752 | 用户说：测试用途 | 相关 |
| 0.742 | 修复后测试成功 | 相关 |
| 0.712 | 用户表示这是测试用途... | 相关 |

**分析**：当 query 中关键词（"测试"）与记忆内容高度重叠时，召回质量良好，最高分达 0.82。说明 embedding 模型对显式关键词匹配稳定，但对语义推断（"有问题" → 需要修复 → 测试）会引入噪声。

## 分数分布特征

基于上述 3 个案例的观察：

| 场景 | 最高分 | 最低分 | 分数区间 |
|------|--------|--------|----------|
| 高度相关（显式关键词重叠） | 0.82 | 0.71 | 0.71–0.82 |
| 弱相关（近音/近义但不精确） | 0.66 | 0.55 | 0.50–0.66 |
| 语义混淆（意图推断错误） | 0.66 | 0.64 | 0.64–0.66 |

结论：0.65 是当前分数分布的一个自然分界点，超过此分值的结果才有可能具备最低限度的相关性。

## 客户端已实施的缓解措施

1. **分数阈值过滤**（`memory_service.py:SEMANTIC_SCORE_THRESHOLD = 0.65`）：丢弃低于阈值的噪声结果。
2. **标签 rerank**：按用户标签对结果重排序，提升个性化相关性。
3. **仅注入 top 2**（`chat.py:_inject_memory_to_prompt`）：即使过滤后有多条，只取前 2 条注入，减少噪声。
4. **低置信度放弃注入**：过滤后全部低于阈值时，不注入任何语义记忆（比注入错误信息更好）。

## MCP 服务端潜在改进方向

1. **升级 embedding 模型**：当前模型在中文短文本语义区分上表现不足，"有问题"被混淆为"测试"。建议评估 BGE-M3 / stella-base-zh 等中文优化模型。
2. **支持 `min_score` 参数**：允许客户端指定最低分数阈值，在服务端过滤，减少无效数据传输。
3. **支持 `filter` 参数**：允许按 metadata 字段过滤（如时间范围、记忆类型），缩小搜索空间。
4. **混合检索（Hybrid Search）**：结合 BM25 关键词检索 + 向量检索，对短文本查询提升召回精度。
5. **返回结果中附带更多元数据**：如记忆的 scene、emotion、时间戳等，供客户端做二次过滤。
