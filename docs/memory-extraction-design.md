# 记忆提取方案设计：从规则到 AI 的混合策略

> 本文档记录夸夸 Agent 记忆提取系统的行业调研、方案选型与技术设计。
> 对应实施：里程碑提取、偏好自动更新、情绪识别的 AI 化改造。

---

## 一、行业调研：主流 Agent 产品怎么做记忆提取

### 1.1 产品对比总览

| 产品 | 提取方式 | 偏好更新 | 里程碑检测 | 核心理念 |
|------|---------|---------|-----------|---------|
| **ChatGPT Memory** | 二次 LLM 调用（小模型） | 自动从对话推断 | 无专门机制 | "让模型自己决定什么值得记" |
| **Replika** | 情绪追踪 + 显式引导 | 隐式 + 显式混合 | 关系里程碑（天数） | "陪伴感 > 信息量" |
| **Character.AI** | 用户自述为主 | 前端配置 | 无 | "角色一致性 > 记忆深度" |
| **Pi (Inflection)** | 对话线索追踪 | 轻量推断 | 无 | "共情优先，记忆为辅" |
| **MemGPT/Letta** | LLM 自主管理 | 函数调用式写入 | 自定义 | "Agent 自己决定存什么" |

### 1.2 ChatGPT Memory：行业标杆

**做法**：每次对话结束后，用一个独立的 LLM 调用（通常是 GPT-4o-mini）审查对话内容，提取结构化的记忆片段。

```
对话结束
    │
    ▼
┌─────────────────────────┐
│ 二次 LLM 调用            │
│ "从以下对话中提取值得     │
│  记住的事实，返回JSON"    │
└──────────┬──────────────┘
           │
           ▼
┌─────────────────────────┐
│ 结构化记忆片段            │
│ "用户偏好Python"          │
│ "用户在准备面试"          │
│ "用户不喜欢冗长回复"      │
└──────────┬──────────────┘
           │
           ▼
     注入下次 system prompt
```

**为什么这样做**：
- ChatGPT 的产品定位是**通用助手**，用户群体庞大，偏好表达千差万别
- 规则无法覆盖自然语言的多样性（"我不太喜欢太长的回答" vs "简短点" vs "别啰嗦"）
- 用小模型做二次提取，成本可控（~$0.001/次），质量远超规则
- 用户可以查看、编辑、删除记忆，形成闭环

**适用夸夸 Agent 的点**：提取思路可借鉴，但 ChatGPT 不做情绪追踪和里程碑，这恰恰是夸夸场景的核心。

### 1.3 Replika：情绪陪伴型

**做法**：
- 显式引导：主动问用户"今天心情如何？""有什么开心的事吗？"
- 隐式追踪：通过对话模式识别情绪趋势（连续3天焦虑 → 标记为高压期）
- 里程碑：基于关系天数（"你们已经认识100天了"），而非内容提取

**为什么这样做**：
- Replika 定位是**情感陪伴**，核心价值是"被记住"的感觉
- 用户粘性来自关系深度，而非信息准确性
- 过度自动提取会让用户觉得"被监视"，所以偏好以显式为主

**适用夸夸 Agent 的点**：情绪追踪和"被记住"的感觉，正是夸夸产品的核心体验。

### 1.4 Character.AI：角色一致性优先

**做法**：记忆很简单，主要靠用户在角色卡里填写的设定。对话中的信息提取很轻量。

**为什么这样做**：
- 定位是**角色扮演**，用户要的是"这个角色活了"，不是"这个角色了解我"
- 过多的记忆反而破坏角色一致性（一个中世纪骑士不应该知道你的工作压力）

**不适用夸夸 Agent**：夸夸产品恰恰需要深度了解用户才能夸得真诚。

### 1.5 MemGPT/Letta：Agent 自主管理

**做法**：LLM 通过函数调用自主决定何时存储、检索、遗忘记忆。分为工作记忆、归档记忆、回忆记忆三层。

**为什么这样做**：
- 定位是**研究型/开发者框架**，追求架构优雅和理论完整性
- 适合复杂 Agent 场景，但对夸夸产品来说过度工程化

**适用夸夸 Agent 的点**：分层记忆的理念（短期对话 + 用户画像 + 长期里程碑）可以借鉴。

## 二、为什么行业都选择 LLM 提取而非纯规则

### 2.1 根本原因：自然语言的歧义性

用户表达同一个意思的方式千变万化：

| 用户说的 | 关键词匹配 | LLM 理解 |
|---------|-----------|---------|
| "今天终于把项目交付了" | 匹配"完成" | 成就：项目交付，情绪：如释重负 |
| "搞定了哈哈" | 匹配"搞定" | 成就：某事完成，情绪：开心 |
| "活过来了" | 不匹配 | 成就：度过难关，情绪：疲惫但满足 |
| "还行吧，就那样" | 不匹配 | 无成就，情绪：平淡/轻微消极 |
| "感觉自己在原地踏步" | 匹配"进步"（误判） | 无成就，情绪：焦虑/自我怀疑 |

最后一行是关键词匹配的致命缺陷——"原地踏步"包含"进步"，但意思完全相反。

### 2.2 成本不再是障碍

| 方案 | 单次成本 | 延迟 | 质量 |
|------|---------|------|------|
| 关键词匹配 | ¥0 | <1ms | 低（误判多、漏判多） |
| LLM 提取（DeepSeek-V3） | ~¥0.001 | 200-500ms | 高 |
| LLM 提取（更便宜的模型） | ~¥0.0003 | 100-300ms | 中高 |

夸夸 Agent 的后台任务已经是异步执行（`asyncio.create_task`），延迟不阻塞用户响应。成本方面，即使日活 1 万用户每天 10 轮对话，月成本也仅 ¥300。

### 2.3 夸夸产品的特殊需求

夸夸产品与其他 Agent 的本质区别：**输出质量直接取决于对用户的理解深度**。

- 通用助手（ChatGPT）：记忆是锦上添花，没有也能用
- 角色扮演（Character.AI）：记忆可能破坏角色一致性
- **夸夸 Agent**：记忆是核心竞争力，"夸得真诚"的前提是"真正了解你"

一个没有记忆的夸夸产品，和网上随便搜的"夸人文案"没有区别。

## 三、夸夸 Agent 的产品定位与提取策略

### 3.1 产品定位决定提取策略

```
夸夸 Agent 的核心价值 = 真诚感 × 个性化 × 即时性
                        ↓         ↓          ↓
                   需要情绪识别  需要偏好记忆  需要快速响应
                        ↓         ↓          ↓
                   LLM 提取    LLM 提取    异步处理
```

**真诚感** → 需要理解用户真实情绪（不是关键词能搞定的）
**个性化** → 需要从对话中自动学习偏好（不是等用户手动配置的）
**即时性** → 提取不能阻塞主流程（后台异步执行）

### 3.2 提取什么？为什么？

| 提取维度 | 为什么需要 | 示例 |
|---------|-----------|------|
| **情绪状态** | 调整夸赞语气（焦虑时安慰、开心时共鸣） | "疲惫" → 下次夸赞时先说"辛苦了" |
| **偏好标签** | 个性化夸赞方向（努力型 vs 天赋型） | ["程序员","考研中"] → 夸技术能力或学习毅力 |
| **场景倾向** | 自动选择 prompt 模板 | 经常聊工作 → 默认 career 场景 |
| **里程碑** | 记住成就，后续可回顾和引用 | "通过了面试" → 下次提到"还记得你面试时…" |
| **禁忌词** | 避免触发用户敏感点 | 用户反感"加油" → prompt 中排除 |

### 3.3 不做什么？

- **不做深度心理分析**：夸夸 Agent 不是心理咨询产品，不需要诊断用户心理状态
- **不做长期行为预测**：不需要预测用户未来行为，只需要记住过去
- **不做跨用户画像**：每个用户的记忆完全隔离

## 四、技术方案：混合提取引擎

### 4.1 架构设计

```
用户消息 + AI 回复（后台任务）
    │
    ▼
┌─────────────────────────────────┐
│  第1层：关键词快速匹配（<1ms）     │
│  - 成就关键词命中 → 直接提取       │
│  - 情绪关键词命中 → 直接标记       │
│  - 命中 → 跳过 LLM，省成本        │
└──────────┬──────────────────────┘
           │ 未命中
           ▼
┌─────────────────────────────────┐
│  第2层：LLM 结构化提取（200-500ms）│
│  单次调用，同时提取：              │
│  - 情绪状态                       │
│  - 偏好标签                       │
│  - 里程碑 + 重要性评分            │
│  - 场景倾向                       │
│  返回 JSON，解析后写入数据库       │
└──────────┬──────────────────────┘
           │ 调用失败
           ▼
┌─────────────────────────────────┐
│  第3层：降级为无提取               │
│  不影响主流程，下次重试            │
└─────────────────────────────────┘
```

### 4.2 为什么是"关键词兜底 + LLM 主力"而不是纯 LLM

| 考量 | 纯 LLM | 混合方案 |
|------|--------|---------|
| 网络故障时 | 完全不可用 | 关键词仍工作 |
| API 限流时 | 阻塞或失败 | 关键词兜底 |
| 明确句式（"我完成了XX"） | 浪费 token | 关键词秒处理 |
| 模糊表达（"活过来了"） | 正确理解 | LLM 处理 |
| 月成本（1万日活） | ¥300 | ¥150-200（部分被关键词拦截） |

### 4.3 LLM 提取 Prompt 设计

```python
EXTRACTION_SYSTEM_PROMPT = """你是一个记忆提取助手。分析用户消息和AI回复，提取结构化信息。

返回严格JSON格式，不要任何解释：
{
  "has_milestone": false,
  "milestone_content": null,
  "milestone_importance": 0,
  "emotion": "neutral",
  "emotion_intensity": 0.5,
  "tags": [],
  "scene_hint": null,
  "avoid_words": []
}

字段说明：
- has_milestone: 用户是否提到了自己的成就、进步、突破
- milestone_content: 成就的简短描述（20字以内），无成就时为null
- milestone_importance: 1-5，1=小事，5=人生大事
- emotion: 用户当前情绪，用一个词描述（开心/焦虑/疲惫/平静/兴奋/低落/自信/迷茫...）
- emotion_intensity: 0-1，情绪强度
- tags: 从对话中提取的用户标签（职业、兴趣、状态等），最多3个
- scene_hint: 推断场景 career/beauty/love/daily/null
- avoid_words: 用户表达反感的词汇，没有则为空数组

注意：
- 只提取用户明确表达或强烈暗示的信息，不要过度推断
- "还行""一般""凑合"这类模糊表达，emotion应为"neutral"
- 反讽、自嘲（"我真是个天才"在失败语境下）不要误判为正面情绪"""
```

### 4.4 关键词兜底层设计

```python
# 成就关键词（现有 + 扩展）
ACHIEVEMENT_KEYWORDS = [
    "完成", "达成", "通过", "拿到", "获得", "坚持", "成功",
    "突破", "进步", "提升", "搞定", "拿下", "上岸", "过线",
    "录用", "offer", "录取", "升职", "加薪", "获奖",
]

# 情绪关键词映射
EMOTION_KEYWORDS = {
    "开心": ["开心", "高兴", "快乐", "爽", "太好了", "哈哈", "嘿嘿"],
    "焦虑": ["焦虑", "紧张", "担心", "怕", "慌", "压力大"],
    "疲惫": ["累", "疲惫", "加班", "熬夜", "撑不住", "倦"],
    "低落": ["难过", "丧", "低落", "不开心", "烦", "郁闷"],
    "自信": ["自信", "有底气", "感觉不错", "稳了"],
}

# 成就关键词（否定/反义，用于排除误判）
NEGATION_KEYWORDS = ["没有", "没", "不", "未", "别", "没有", "还没"]
```

### 4.5 提取结果写入

一次 LLM 调用的结果，写入三个地方：

```python
# 1. 里程碑表（如果 has_milestone=true）
if result.has_milestone:
    await memory_service.add_milestone(MilestoneCreate(
        user_id=user_id,
        content=result.milestone_content,
        source="ai_extract",
        importance=result.milestone_importance,
    ))

# 2. 用户画像表（更新情绪和标签）
await memory_service.update_user_profile(user_id, UserProfileUpdate(
    last_emotion=result.emotion,
    user_tags=result.tags if result.tags else None,
    prefer_scene=result.scene_hint,
))

# 3. 语义记忆（带上情绪标签存入 supermemory）
await memory_service.save_chat_to_supermemory(
    user_id=user_id,
    user_message=user_message,
    ai_response=ai_response,
    scene=result.scene_hint or scene,
    emotion=result.emotion,
)
```

### 4.6 配置项设计

```env
# .env 新增配置

# 提取用模型（可以和夸夸生成用同一个，也可以用更便宜的）
AI_EXTRACT_MODEL=deepseek-ai/DeepSeek-V3.2

# 是否启用 AI 提取（false 时回退到纯关键词）
AI_EXTRACT_ENABLED=true

# 是否启用关键词兜底层（false 时纯 LLM）
AI_EXTRACT_KEYWORD_FALLBACK=true

# 提取 LLM 的 temperature（越低越确定性）
AI_EXTRACT_TEMPERATURE=0.1

# 提取 LLM 的 max_tokens
AI_EXTRACT_MAX_TOKENS=200
```

## 五、成本与性能预估

### 5.1 单次提取成本

| 项目 | Token 数 | 单价（DeepSeek-V3） | 成本 |
|------|---------|-------------------|------|
| 系统 Prompt | ~300 | ¥0.001/1K | ¥0.0003 |
| 用户消息 | ~100 | ¥0.001/1K | ¥0.0001 |
| AI 回复 | ~50 | ¥0.001/1K | ¥0.00005 |
| 输出 JSON | ~100 | ¥0.002/1K | ¥0.0002 |
| **合计** | ~550 | | **~¥0.0007** |

### 5.2 规模预估

| 日活用户 | 日对话轮次 | 日提取次数 | 月成本 |
|---------|-----------|-----------|--------|
| 1,000 | 5,000 | ~3,500（30%被关键词拦截） | ¥75 |
| 10,000 | 50,000 | ~35,000 | ¥750 |
| 100,000 | 500,000 | ~350,000 | ¥7,500 |

### 5.3 延迟影响

- 后台任务已异步执行，**不阻塞用户响应**
- LLM 提取 200-500ms，叠加在后台任务中，用户无感知
- 关键词匹配 <1ms，几乎无开销

## 六、与现有架构的兼容性

### 6.1 不需要改的

- `MemoryService` 的 CRUD 接口不变
- `MemorySummary` 的数据结构不变
- `chat_service.py` 的 prompt 注入逻辑不变
- supermemory MCP 集成不变
- 前端 API 接口不变

### 6.2 需要改的

| 文件 | 改动 |
|------|------|
| `app/config.py` | 新增 AI_EXTRACT_* 配置项 |
| `.env` | 新增配置值 |
| `app/services/memory_service.py` | 新增 `MemoryExtractor` 类，重构 `extract_and_add_milestone()` |
| `app/api/chat.py` | `_update_session_after_chat()` 接入提取引擎 |
| `app/services/cloudbase_memory.py` | 同步更新里程碑提取逻辑 |

### 6.3 回滚策略

- 配置 `AI_EXTRACT_ENABLED=false` 即可回退到纯关键词模式
- 关键词列表作为兜底，永远可用
- 提取失败时自动降级，不影响主流程

## 七、后续演进方向

| 阶段 | 内容 | 时机 |
|------|------|------|
| **Phase 1（当前）** | 混合提取引擎上线 | 即刻 |
| **Phase 2** | 基于提取结果优化 prompt 注入（情绪感知的夸赞） | 提取数据积累后 |
| **Phase 3** | 里程碑去重和重要性衰减 | 里程碑数量 > 50/用户 |
| **Phase 4** | 用户可查看和编辑自己的"记忆卡片" | 前端功能迭代 |
| **Phase 5** | 多轮对话的上下文感知提取（不只看当前轮） | 会话记忆增强后 |
